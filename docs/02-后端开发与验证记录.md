### 2.2 关键设计验证（这几条最能说明设计是否站得住）

**① 逻辑删除 + `(sku, deleted)` 唯一索引**

```text
插入 SKU=TEST-DEL-0001 的未删除商品               -> 成功（id=7, deleted=0）
再插入同一 SKU 的未删除商品                       -> ERROR 1062 Duplicate entry 'TEST-DEL-0001-0'（唯一索引生效）
逻辑删除（deleted = id）后再插入同一 SKU          -> 成功（id=9, deleted=0）
查询结果： id=7 deleted=7（历史记录保留）  id=9 deleted=0（新的活跃记录）
```

结论：`deleted` 写入主键 ID 的策略确实同时满足「活跃数据唯一」与「保留历史删除记录」，
普通 `deleted=0/1` 方案做不到这一点。

**② 库存 CHECK 约束**

```text
UPDATE inventory SET available_stock = -1
-> ERROR 3819 Check constraint 'chk_available_stock' is violated.
```

**③ 防超卖的条件更新（与 InventoryMapper 中完全相同的 SQL）**

```text
库存 500，扣减 999 -> ROW_COUNT() = 0（更新失败，业务层据此抛"库存不足"）
库存 500，扣减 10  -> ROW_COUNT() = 1，结果 available=490, locked=10
```

## 3. 过程中发现并修复的问题

### 3.1 JWT 过滤器未挂载到安全链（严重）

**现象**：登录成功拿到 Token 后，所有带 Token 的请求仍然返回 401。

**定位过程**：观察服务端日志发现，带 Token 的请求直接落到 `RestAuthenticationEntryPoint`，
且没有触发任何权限加载日志，说明认证过滤器根本没参与到 Spring Security 的过滤器链。

**根因**：`JwtAuthenticationFilter` 被标注为 `@Component` 并继承 `OncePerRequestFilter`，
Spring Boot 把它当作普通 Servlet 过滤器自动注册，默认顺序在安全链之后
（安全链 order = -100）。请求先被安全链判定为未认证并拒绝，过滤器还没来得及解析令牌。

**修复**：
1. 在 `SecurityConfig` 中显式 `http.addFilterBefore(jwtAuthenticationFilter, UsernamePasswordAuthenticationFilter.class)`；
2. 在 `WebMvcConfig` 中注册一个 `setEnabled(false)` 的 `FilterRegistrationBean`，关闭自动注册，避免重复执行；
3. 顺带完善 `RestAuthenticationEntryPoint`，让 401 能区分「未携带令牌(40101) / 已过期(40102) / 非法或已登出(40103)」，
   前端据此决定「跳登录页」还是「静默刷新后重试」。

**验证**：修复后未携带 Token 返回 40101、伪造 Token 返回 40103，正常 Token 可以访问业务接口。

### 3.2 幂等键写 Redis 失败会阻断下单（健壮性）

原实现中幂等 `SETNX` 直接调用 Redis，Redis 抖动会导致下单整体失败。
已改为「Redis 异常时降级」：记录告警并放行，由数据库 `(user_id, request_no)` 唯一索引兜底，保证核心链路可用。
