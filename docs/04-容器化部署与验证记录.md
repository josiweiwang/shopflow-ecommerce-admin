# ShopFlow 容器化部署与验证记录（Step 6）

> 目标：在任意一台装了 Docker 的机器上，一条命令拉起「前端 + 后端 + MySQL + Redis」完整环境。

---

## 1. 一键启动

```bash
cp .env.example .env      # 按需修改端口与密码
docker compose up -d --build
```

启动后：

| 入口 | 地址 | 说明 |
| --- | --- | --- |
| 前端 | http://localhost:8080 | 浏览器访问后台管理系统 |
| 后端接口 | http://localhost:18080 | 直连调试用（生产配置已关闭 Swagger） |
| MySQL | localhost:13306 | 用客户端连库排查问题时使用 |
| Redis | localhost:16379 | 同上 |

演示账号：`admin / Admin@123456`、`operator / Operator@123456`、`demo / User@123456`

停止与清理：

```bash
docker compose down          # 停止容器，保留数据
docker compose down -v       # 连数据卷一起删除（数据库会被重新初始化）
```

## 2. 服务拓扑

```text
浏览器
  │  http://localhost:8080
  ▼
web (Nginx:80)  ── 静态资源 + history 路由回退
  │  /api/** 反向代理
  ▼
api (Spring Boot:8080, 非 root 用户运行)
  │                    │
  ▼                    ▼
mysql:3306          redis:6379
(数据卷持久化)       (AOF 持久化)
```

## 3. 编排设计要点

| 设计 | 目的 |
| --- | --- |
| `healthcheck` + `depends_on: condition: service_healthy` | 应用不会在数据库还没就绪时启动，避免启动即失败 |
| 多阶段构建（Maven 构建 / Nginx 构建 → JRE、Nginx 运行） | 运行镜像不含 JDK、Maven、node_modules 与源码 |
| 后端以非 root 用户运行 | 降低容器被攻破后的影响面 |
| `mysql-data` / `redis-data` 数据卷 | 容器重建不丢数据 |
| `schema.sql` / `data.sql` 挂载到 `docker-entrypoint-initdb.d` | 首次启动自动建表并写入演示数据，做到开箱即用 |
| 敏感配置全部走 `.env` | 密码与 JWT 密钥不进代码库（`.env` 已被 gitignore） |
| Nginx 同源代理 `/api` | 浏览器视角前后端同源，从根上避免跨域问题 |
| `index.html` 不缓存 + 带 hash 资源长缓存 | 发版即时生效，同时保留静态资源缓存收益 |

镜像体积：

| 镜像 | 体积 |
| --- | --- |
| `shopflow/api:1.0.0` | 527 MB（含 JRE 17 与全部依赖） |
| `shopflow/web:1.0.0` | 77.3 MB（Alpine Nginx + 构建产物） |

## 5. 部署过程中发现并修复的两个问题

### 5.1 容器初始化时中文被双重编码（数据正确性问题）

**现象**：容器内初始化后，数据库中 `系统管理员` 被存成了 `ç³»ç»Ÿç®¡ç†å‘˜`，
HEX 值为 `C3A7C2B3...`（而不是正确的 `E7B3BB...`），接口返回给前端的也是乱码。

**根因**：MySQL 官方镜像的入口脚本执行 `.sql` 文件时，客户端连接的字符集取决于客户端默认值（常为 latin1）。
`schema.sql` 我写了 `SET NAMES utf8mb4;`，但 `data.sql` 漏了，
于是 UTF-8 的中文字节被当作 latin1 解释后又以 utf8mb4 存库，形成双重编码。

**修复**：在 `data.sql` 开头补上 `SET NAMES utf8mb4;`，并重建数据卷验证——
修复后 HEX 为 `E7B3BBE7BB9FE7AEA1E79086E59198`（即 `系统管理员`），接口返回正常。

**经验**：这类问题在本地开发（客户端已配置 utf8mb4）完全看不出来，
只有真正走"从零初始化部署"这条路径才会暴露，属于必须做一次容器化验证才能发现的坑。

### 5.2 容器健康检查失败（IPv6 解析）

**现象**：`shopflow-web` 一直停留在 `health: starting`，
容器内 `wget http://localhost/` 报 `Connection refused`，但宿主机访问 `http://localhost:8080` 正常。

**根因**：容器 `/etc/hosts` 中 `localhost` 同时映射到 `127.0.0.1` 与 `::1`，
busybox 的 wget 优先尝试 IPv6 的 `::1`，而 Nginx 默认只监听 IPv4（`0.0.0.0:80`），因此被拒绝。

**修复**：健康检查地址改为显式的 `http://127.0.0.1/`（后端健康检查一并改成 `127.0.0.1:8080`），
重新构建后四个容器全部 `healthy`。
