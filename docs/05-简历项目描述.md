## 一、写入简历的项目条目

### 写法一：三条要点（推荐，与现有项目风格一致）

**ShopFlow 电商后台管理系统（企业级 Web 应用）**
技术栈：Java / Spring Boot 3 / MyBatis-Plus / MySQL 8 / Redis / JWT / Vue 3 / Docker

• 基于 Spring Boot 3 + MyBatis-Plus + MySQL 8 + Redis 构建前后端分离的电商后台系统，按 controller/service/mapper 分层并隔离 Entity/DTO/VO 三态模型，统一实现全局异常处理、参数校验与响应体规范；设计含 RBAC 权限、商品库存、订单与审计的 13 张表 ER 模型，并用订单明细快照保障历史订单不受商品变更影响。

• 针对下单超卖问题设计三层防护：Redis Lua 脚本原子预扣库存、MySQL 条件更新（`WHERE available_stock >= n`）作为最终防线、CHECK 约束与库存流水对账兜底；100 并发抢 100 件库存实测 200 次请求成功 100 笔，零超卖、零负库存、无重复订单。

• 用 Cache-Aside 优化商品详情热点读，以空值占位防穿透、SETNX 互斥防击穿、TTL 抖动防雪崩，实测吞吐由 2536 QPS 提升至 8569 QPS（3.4 倍）、P95 延迟降低 74%；并用压测定位下单瓶颈为库存行锁竞争（多商品打散后 100 → 293 QPS），梳理出库存分桶与异步化的优化路径。

### 写法二：四条要点（版面充足、想突出后端深度时）

• 使用 Spring Boot 3 + MyBatis-Plus + MySQL 8 + Redis 实现商品、库存、订单、权限、数据看板五大模块，按 controller/service/mapper 分层并隔离 Entity/DTO/VO 三态模型，落地全局异常处理、参数校验、统一响应体与 TraceId 链路追踪。

• 完成 13 张表的数据库设计：用户-角色-权限 RBAC 模型、商品与库存一对一拆表、订单明细商品快照、库存与订单状态流水审计；通过 `(sku, deleted)` 组合唯一索引配合"逻辑删除写入主键 ID"的策略，同时满足活跃数据唯一与历史记录保留。

• 设计并实现三层防超卖方案（Redis Lua 原子预扣 → MySQL 条件更新 → CHECK 约束兜底），配合 Redis SETNX + 数据库唯一索引实现幂等下单、事务回滚时回补缓存库存；100 并发抢 100 件库存实测零超卖，重复提交只产生一笔订单。

• 基于 Cache-Aside + 互斥回源优化热点读，吞吐提升 3.4 倍（2536 → 8569 QPS）、P95 降低 74%；使用自研压测工具完成 20 万数据下的深分页实验，验证游标分页较 OFFSET 深分页快约 570 倍；通过 docker-compose 多阶段构建实现全栈一键部署（四容器健康检查通过）。

### 写法三：英文版（投递英文简历或英文岗时使用）

**ShopFlow — E-commerce Admin System (Full-stack, Backend-focused)**
Tech: Java 17 / Spring Boot 3 / MyBatis-Plus / MySQL 8 / Redis 7 / JWT / Vue 3 / Docker

• Built a layered e-commerce admin backend (controller/service/mapper with strict Entity/DTO/VO separation) on Spring Boot 3 + MyBatis-Plus + MySQL 8 + Redis, covering product, inventory, order, RBAC and dashboard modules, with unified exception handling, request validation and API response conventions.

• Designed a 13-table schema including an RBAC model, a 1:1 product-inventory split, immutable order-item snapshots and inventory/order-status audit logs; used a `(sku, deleted)` unique index with logic-delete-writes-PK to keep active rows unique while preserving deletion history.

• Prevented overselling with three layers — atomic Redis Lua stock reservation, conditional MySQL update (`WHERE available_stock >= n`) and CHECK constraints with reconciliation logs; verified with 100 concurrent buyers competing for 100 units: exactly 100 orders succeeded, zero oversold, zero negative stock.

• Improved hot-read throughput 3.4× (2,536 → 8,569 QPS, P95 -74%) with Cache-Aside plus null-value caching, mutex-based rebuild and jittered TTL; profiled order creation to identify inventory row-lock contention as the bottleneck (100 → 293 QPS when traffic is spread across products).

## 二、面试展开点（每条都能给出数据或代码）

| 面试官可能问 | 你可以怎么答 |
| --- | --- |
| 防超卖是怎么做的？为什么不用乐观锁或直接 `UPDATE stock = stock - 1`？ | 三层防护。直接减法会超卖；高并发下乐观锁 version 冲突会导致大量重试、成功率下降，所以用 Redis Lua 把并发收敛在缓存层，数据库条件更新只作为最终防线。实测 200 并发抢 100 件，成功恰好 100 笔，库存表最小值为 0，没有负数。 |
| 缓存和数据库不一致怎么办？ | 明确承认是最终一致：商品详情用 Cache-Aside 删除 + 事务提交后延迟双删；库存用 Redis 为准 + 定时对账（`inventory_log` 可推算库存）。接口用 `fromCache` 字段显式标记数据来源，不假装强一致。 |
| 缓存三大问题怎么处理？ | 穿透：不存在的 ID 缓存空值 TTL 5 分钟；击穿：回源加 SETNX 互斥锁 + 双重检查 + 未抢锁请求短暂轮询；雪崩：TTL 加随机抖动。命中率实测 100%（122,230 命中 / 0 未命中）。 |
| 下单接口的瓶颈在哪？怎么定位的？ | 并发从 50 提到 100，吞吐只从 70 涨到 100 QPS——典型的"加并发不加吞吐"。把流量打散到 4 个商品、其他条件不变，吞吐涨到 293 QPS，由此定位到**同一商品库存行的行锁串行化**。顺带排除了一个直觉误区：以为 dev 打印 SQL 日志拖慢，换 prod 配置复测吞吐几乎没变。 |
| 幂等怎么保证？ | Redis SETNX（24h）+ 数据库 `(user_id, request_no)` 唯一索引双保险；Redis 异常时降级为只靠唯一索引，不让缓存故障阻断下单。 |
| 为什么订单明细要存商品名称和价格？ | 快照。商品改价、改名、下架、删除都不应影响历史订单展示与金额，所以订单详情不 JOIN 商品表。 |
| 逻辑删除为什么用 `deleted = id` 而不是 `0/1`？ | 如果用 `deleted TINYINT`，`UNIQUE KEY (sku, deleted)` 无法支持"同一 SKU 被删除两次"，活跃数据唯一约束也会失效。写入主键 ID 后，唯一索引同时满足活跃唯一与历史保留，已用真实 MySQL 验证（重复 SKU 报 1062，删除后同 SKU 可重新上架）。 |
| 权限是怎么做的？ | RBAC 五张表 + 自定义 `@RequirePermission` 注解 + AOP；用户-角色-权限三次 JOIN 的结果缓存 30 分钟，角色变更立即失效；订单等接口额外做数据归属校验防水平越权。前端菜单由"路由表 + 用户权限"推导，不会出现菜单能点但接口 403。 |
| JWT 怎么做登出和续期？ | 双令牌：access 30 分钟、refresh 7 天且存 Redis。登出把 access 的 jti 写入黑名单（TTL = 剩余有效期），重建 refresh。401 响应区分 40101/40102/40103，前端据此决定跳登录还是静默刷新。 |
| 这个项目最难的坑是什么？ | 举部署期发现的两个：① 容器初始化时 `data.sql` 缺 `SET NAMES utf8mb4`，中文被双重编码存库（HEX 校验 C3A7… 而非 E7B3…），本地开发完全看不出来；② JWT 过滤器被 Spring Boot 当作普通 Servlet 过滤器注册，顺序排在安全链之后，导致带 Token 的请求全部 401——这两个问题都只有真跑起来才会暴露。 |
| 深分页怎么优化？ | 20 万数据实测：OFFSET 10 万扫描 100,010 行/30.2ms；延迟关联只快 18%（扫描行数没变）；游标分页只扫描 10 行/0.053ms，快约 570 倍。后台列表保留 OFFSET（限制最大页深），C 端流式列表用游标。 |
| 怎么保证代码质量？ | 36 个测试用例：状态机穷举、JWT 边界、统一响应、上下文冒烟、以及 200 并发防超卖集成测试（Testcontainers）；构建前前端强制 `vue-tsc` 类型检查；读接口全部走统一响应体与错误码规范。 |
