## 2. 商品详情缓存收益（Cache-Aside 是否值得）

同一接口、同一并发（50）、同时长（20s），只切换缓存开关：

| 场景 | 总请求数 | QPS | 平均延迟 | P95 | P99 |
| --- | --- | --- | --- | --- | --- |
| 缓存 **开启** | 171,414 | **8,570** | 5.8 ms | 13.3 ms | 24.0 ms |
| 缓存 **关闭**（每次回源数据库） | 50,734 | **2,536** | 19.7 ms | 52.6 ms | 87.7 ms |
| 缓存开启（prod 配置复核） | 129,300 | 8,619 | 5.8 ms | 13.9 ms | 20.6 ms |

**结论**：缓存把吞吐提升了 **3.4 倍**（8,570 vs 2,536 QPS），P95 降低 **74%**，平均延迟降低 **71%**。

**缓存命中率**（Micrometer 指标，`/actuator/metrics/shopflow.product.cache.hit`，预热后统计）：

```text
shopflow.product.cache.hit     = 122,230
shopflow.product.cache.miss    = 0
shopflow.product.cache.rebuild = 0
=> 命中率 100%
```

命中率能做到 100%，是因为代码里做了三件事：空值占位防穿透、SETNX 互斥防击穿、TTL 随机抖动防雪崩。

## 3. 并发下单与防超卖（正确性验证）

**场景**：商品 1 库存重置为 100，100 并发同时下单 200 次，每次 1 件。

```text
总请求数=200 成功=100 失败=100
业务码分布: 200=100  60001=100        （60001 = 库存不足）
```

数据库最终状态（并发压测后直接查库）：

| 校验项 | 结果 | 是否符合预期 |
| --- | --- | --- |
| 订单数 | 100 | ✅ 恰好等于库存数 |
| 商品1 可用 / 锁定 / 总库存 | 0 / 100 / 100 | ✅ 库存归零、锁定数正确 |
| 全表最小可用库存 / 最小锁定库存 | 0 / 0 | ✅ **无负数库存，零超卖** |
| 锁定类型库存流水条数 | 100 | ✅ 与成功订单数一致，可追溯 |
| `request_no` 去重后数量 / 订单总数 | 100 / 100 | ✅ 无重复订单 |

这说明三层防护（Redis Lua 原子预扣 → MySQL 条件更新 → CHECK 约束）在真实并发下确实成立：
200 个并发请求里，只有 100 个能通过校验，其余 100 个在缓存层就被拒绝，根本没打到数据库。

## 4. 下单吞吐与瓶颈定位（本次最有价值的发现）

### 4.1 实测数据

| 场景 | 并发 | 请求数 | QPS | 平均延迟 | P95 |
| --- | --- | --- | --- | --- | --- |
| 同一商品（dev 配置） | 50 | 500 | 82.8 | 575 ms | 888 ms |
| 同一商品（prod 配置） | 50 | 500 | 70.7 | 679 ms | 1,093 ms |
| 同一商品（prod，并发翻倍） | 100 | 1,000 | 100.2 | 952 ms | 1,114 ms |
| **4 个商品打散流量** | 100 | 1,000 | **293.1** | 324 ms | 383 ms |

### 4.2 定位过程

并发从 50 提到 100，吞吐只从 70 涨到 100 QPS——典型的"加并发不加吞吐"，说明存在串行化瓶颈。
于是把流量打散到 4 个商品，同一时刻其他条件完全不变，吞吐直接涨到 **293 QPS（2.9 倍）**。

**结论：瓶颈是同一商品库存行的行锁串行化。**

原因很直接：`UPDATE inventory ... WHERE product_id = ?` 会对该商品的库存行加排他锁，
并且锁一直持有到事务提交。而出库下单的事务里，加锁之后还有「查询库存、写库存流水、写订单、写订单明细、写状态流水、提交」等多次数据库往返，
这段时间内所有针对同一商品的订单都在排队。

### 4.3 优化方向（按性价比排序）

1. **缩短持锁时间**：把库存行 `UPDATE` 尽量放到事务最后，加锁后只做必要的写入；
   例如扣除掉加锁后的那次冗余 `SELECT inventory`（改为加锁前读取，日志用「更新前值 ± 变更量」计算）。
2. **库存分桶**：把一个商品的总库存拆成 N 行（如 10 桶 × 每桶 1/10），下单时路由到不同桶，
   把行锁竞争分散到 N 行上——这是秒杀场景的常规做法。
3. **异步化下单**：请求只做「Redis 预扣 + 落一条消息」，订单在后台线程池/MQ 消费生成，
   接口响应时间与数据库写入解耦（本项目未引入 MQ，属于明确的扩展方向）。
4. 连接池与 Tomcat 线程数按压测结果调优（当前 50 连接在打散场景下并未打满）。

> 顺便排除了一个直觉误区：一开始怀疑是 dev 环境打印全量 SQL 日志拖慢吞吐，
> 换成 prod 配置（关闭 SQL 日志、连接池 50）复测后，吞吐几乎没变（82.8 → 70.7 QPS），
> 证明日志不是瓶颈——这也说明"性能问题要靠数据定位，不能靠猜"。

## 5. 深分页优化（20 万订单实测）

对比三种方案，用 `EXPLAIN ANALYZE` 取服务端实际执行数据：

| 方案 | 扫描行数 | 服务端实际耗时 |
| --- | --- | --- |
| OFFSET 深分页（`LIMIT 100000, 10`） | 100,010 | 30.2 ms |
| 延迟关联（先查主键再回表） | 100,010 | 24.6 ms |
| **游标分页（`WHERE id < 游标值 ORDER BY id DESC LIMIT 10`）** | **10** | **0.053 ms** |
| 浅分页对照（`LIMIT 10`） | 10 | 0.040 ms |

**结论**：

1. `LIMIT offset, size` 的代价随偏移量**线性增长**——MySQL 必须扫描并丢弃前 10 万行；
2. 延迟关联只让耗时下降约 18%（因为扫描行数没变，只是少回表了几列），**不是深分页的正解**；
3. 游标分页的代价与深度**无关**（扫描 10 行 / 0.053ms，比 OFFSET 方案快约 570 倍），
   代价是不能跳页，适合"无限下拉/下一页"场景。

**落地建议**：后台管理列表保留 OFFSET 分页（页码跳转是刚需，且限制最大页深）；
面向 C 端的订单流、商品流改用游标分页。

另外在接口层做了对照：`pageNum=1` 与 `pageNum=10000` 的响应时间分别为 101ms 与 97.6ms，
几乎无差异——因为当前固定开销（鉴权过滤器的 Redis 往返、JSON 序列化、分页 count）远大于深分页本身的代价。
所以**当前阶段的接口瓶颈不在分页，而在每请求的固定开销**，这也是后面要继续优化的方向。

## 6. 已落地的优化清单

| 优化项 | 手段 | 效果 |
| --- | --- | --- |
| 防超卖 | Lua 原子预扣 + 条件更新 + CHECK 约束 | 200 并发零超卖，失败请求不落库 |
| 商品详情读性能 | Cache-Aside + 空值占位 + SETNX 互斥 + TTL 抖动 | QPS 提升 3.4 倍，命中率 100% |
| 缓存一致性 | 事务提交后延迟双删 | 消除"删缓存后旧值回填"的脏窗口 |
| 下单幂等 | Redis SETNX + 数据库唯一索引双保险 | 重复提交只产生一笔订单；Redis 故障自动降级 |
| 权限查询 | 用户-角色-权限三次 JOIN 结果缓存 30 分钟 | 每个请求避免 3 次 JOIN；角色变更即时失效 |
| 缓存可观测 | Micrometer 计数器 | 命中率可直接从 Actuator 读取 |
| 超时关单 | Redis ZSet 延时队列 | 每分钟只处理真正到期的订单，不扫全表 |
| 日志 | prod 关闭 SQL 打印 + 异步 Appender | 避免 IO 阻塞业务线程 |
| 连接池 | Hikari 池大小按环境区分（dev 20 / prod 50） | 避免压测与生产的配置偏差 |

## 7. 待优化项（诚实清单）

1. **JWT 过滤器每请求一次 Redis EXISTS**（黑名单校验）：高频下是固定开销，
   可改为本地布隆过滤器/本地缓存 + 定期同步，或只在令牌临近过期时校验。
2. **订单明细统计用相关子查询**：订单量继续增长后可冗余 `item_count` / `total_quantity` 字段。
3. **库存热点行**：见 4.3 的分桶方案。
4. **下单链路偏长**（约 8 次数据库往返）：可合并语句或异步化。
5. **Testcontainers 集成测试**：在当前这台机器的 Docker Desktop 上，Java 的 npipe 连接被转发到 CLI 代理而无法建链
   （`docker` CLI 正常），因此该用例自动跳过；换到标准 Docker 环境即可运行，本次的并发验证已用 HTTP 压测等价覆盖。
